# Integrated system workbench

ArchEasy now opens on **System Health**. Use the always-visible, independently scrolling sidebar to access all setup, software, system, personalisation and recovery pages. Software Centre is the existing software browser, with a category menu; Installed, Configs, Gaming Setup, Developer Tools, Cloud Backup and all previous management pages remain available. There is no duplicate store or replacement config manager.

This is for an **installed Arch Linux desktop**, not an automated ISO installer. The Rescue page provides preparation and offline-recovery guidance, not automatic discovery/repair of another mounted installation. Other distributions, immutable installations, container host management and root GUI sessions are unsupported.

## Architecture and permissions

No new Rust dependencies or background daemon. `src/workbench.rs` supplies native GTK pages and Cairo graphs. `scripts/workbench.py` is embedded with the existing management runtime, sharing its structured command runner, filesystem/package checks, private operation records, logs and terminal privilege boundary. Subprocess arguments are arrays; utility output is plain text, never commands or markup.

Health sampling reads `/proc` and `/sys` at a configurable **2–60 seconds** (default five), only while the page is mapped. Polling is serialized and records no file per sample. CPU graph gaps show missing/reset counters. Network rates are bytes/second over consecutive valid counters. Empty GPU/sensor data means unavailable, not zero. Process inspection uses command names rather than full argument strings to reduce accidental credential disclosure. Diagnostic tools have bounded time/output; scans run off the GUI thread. **Cancel scan** requests stop through a private per-operation flag. The helper terminates only a diagnostic subprocess and reports cancellation; atomic package commands are never interrupted by this control. Cancellation is cooperative, and some simple file-read sections finish before observing it.

The GUI stays unprivileged; individual approved official package commands use sudo in the terminal. GNOME settings, power profiles, backlight and migration use normal-user permissions/polkit provided by the native tool. Unsupported/denied operations fail clearly; no tool is installed or service enabled to make a control work.

Official individual install/remove and Flatpak actions, Creator Studio, official updates, the install queue, Gaming Setup and Developer Tools use compatible per-user package/update lock files in `$XDG_RUNTIME_DIR` (cache fallback). Pacman still owns the authoritative machine-wide transaction lock. Other users/tools can race between preflight and execution; pacman must resolve that. No lock is deleted. Legacy single AUR/GitHub and other cleanup workflows retain their existing locking/logging limitations; this is documented rather than claiming global coverage. New official installs use `pacman -Syu --needed`; queue official steps also use full upgrades. Dependency/config removal (`-Rns`) remains an explicit Installed checkbox and a reviewed pacman transaction. Default removal uses `-R`.

Before installing Creator/official packages, the broker checks lock/process evidence, root/cache free space, repositories and local database consistency, then verifies requested packages in configured metadata. Pacman presents the final dependency/size transaction and normal approval/signature checks. Metadata can be stale, and a full upgrade can require a reboot. The 2 GiB preflight floor is not a size estimate. An operation can fail before removal too when its conservative preflight fails; reviewed cleanup in System Utilities is a separate workflow. The existing queue has a shared application lock and pacman lock guard but does not yet share the full broker preflight/logging path. Its terminal asks whether to continue between transactions; completed packages remain installed after cancellation.

Records and streamed terminal output use the management state folder described in [system management](system-management.md). An interrupted record means completion is unknown; inspect logs and pacman transaction markers before retrying. Diagnostic reports may include IP addresses, SSIDs, file paths and hardware identifiers. Export is a local private file, never an upload; review before sharing. No private SSH key or WireGuard configuration is opened. Inline password-like fstab options are redacted, but report redaction is not guaranteed comprehensive.

## Migration workflow and security

1. Enter comma-separated **individual relative files**, such as `.bashrc,.config/kitty/kitty.conf`. Nothing is selected by default. Do not select a directory.
2. Choose a new absolute export JSON path. Optionally include foreign/AUR **names and versions**, never PKGBUILDs.
3. Review the exact paths and approve in the terminal. Files are limited to 1 MiB each, 100 files and 8 MiB total. Only UTF-8 regular user-owned config files are supported. Private output is created exclusively with mode 0600.
4. On the destination machine, enter the manifest path and use **Import / Preview Changes / Compatibility Report**. Inspect conflicts, source hardware/kernel/desktop and package availability yourself. Package lists are data; they are never run as commands.
5. Enter the selected file names and a new staging directory, then approve staging. Verify the contents as untrusted code (shell/editor configs can execute code when later loaded). Nothing is sourced or copied over your live home files automatically.
6. If manually applying a reviewed file, back up its current version first. Use existing Configs workflows where a managed preview/rollback is appropriate. Review packages through Software Centre on the destination rather than executing an imported installer blindly.

The format is `archeasy-migration-v1`, containing source metadata, package data and base64/checksummed file entries, with restored modes fixed to 0600. It is a JSON artifact, not an executable archive. Absolute/traversal/duplicate paths, symlinked selections/ancestors, credential stores, common browser/key locations, known hardware/system config names, checksum errors, oversize files and detected secret assignments/key material are refused. Unknown format/corrupt manifests fail without live writes. Existing portable ZIP path traversal/checksum protections remain tested separately.

Secret detection is conservative and heuristic; it can reject harmless comments or miss custom secrets. Browser profiles/password stores/cloud credentials/keys are not migration defaults; do not try to bypass exclusions to share credentials. Migration JSON is private but **not encrypted**; use independently encrypted storage when transferring. Root-owned files are never restored by this workflow. Checks cannot protect against a malicious process in your own account concurrently replacing parent paths; use a trusted session.

## Dependencies and install

Build/install instructions remain in the [README](../README.md). Python 3 standard library, GTK4/Libadwaita and existing pacman/util-linux tooling are reused. Optional utilities improve individual diagnostics: `smartmontools`, `pciutils`, `btrfs-progs`, `efibootmgr`, systemd tools, `iproute2`, `iw`, NetworkManager, `curl`, `firewalld` **or** UFW, nftables, OpenSSH, WireGuard tools, `power-profiles-daemon`, `brightnessctl`, gsettings and the active desktop's native settings. Do not install competing firewall/power tools just to populate this page. Missing tools are reported. No new always-running monitoring service is required.

ArchEasy does not modify bootloaders, partitions, firewall rules, SSH exposure, lid/logind configuration or charge thresholds. Rescue guidance explains when a live ISO is required. Profile/backlight/color preference changes normally need no reboot; kernel/full upgrades and actual offline recovery may.

## Troubleshooting and verification

- **GPU graph unavailable:** the active driver may not publish `gpu_busy_percent`; use Hardware & Drivers. Do not install another driver just to fill a graph.
- **SMART/firewall/EFI unavailable:** inspect the reported permission/tool error. Absence of a successful read is not a health/security pass.
- **Profile blocked:** review active TLP/tuned/auto-cpufreq services and native hardware support. ArchEasy will not disable them automatically.
- **Migration refused:** inspect file ownership, links, hardware-specific paths or secret findings locally; do not paste secrets into logs/issues.
- **Package lock:** wait for the owner and inspect logs. Never delete a live pacman lock to force progress.

Run `python3 tests/workbench_test.py`, `python3 tests/system_management_test.py`, `cargo test --offline`, `cargo clippy --offline -- -D warnings` and `cargo fmt --all -- --check`. See [verification results and exact commands](workbench-verification.md). CI also runs existing suites and isolated graphical tests. Use a **disposable Arch VM** to verify interactive sudo/pacman/Flatpak approval and logs, metadata/network failures, GNOME apply/revert/conflicts, native settings across desktops, power-profile conflicts, brightness hardware/permissions, sensor gaps, encrypted/multi-boot rescue evidence and external migration staging. No destructive boot/disk/firewall/firmware/restore test belongs on the host.
